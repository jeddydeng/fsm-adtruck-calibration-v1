# 车辆激光雷达 + 摄像头联合外参采集站

本目录是一套独立的标定工具，不参与 `white_ws` 的 colcon 编译。它只会启动
`calibration_lidars.launch.py`、相机接收和标定网页，不会启动 CAN、车辆接口、
规划或控制节点。

## 1. 传感器与安全边界

- 4 路完整原始点云：车顶 32 线、左前 BPearl、右前 BPearl、车尾 BPearl。
- 6 路 640×480 MJPEG USB 相机；每一路独立重连，拔插不会拖垮整个程序。
- 4 路树莓派鱼眼相机；使用 `Pi-capture/fisheye_raw_sdk.py` 相同的 raw-all
  MJPEG 协议，每一路独立重连。
- 1 路 ROS2 压缩图像：
  `/sensing/camera/traffic_light_front/image_raw/compressed`（320×240、5 Hz）。
- 相机识别 `DICT_APRILTAG_16h5` 的 ID 和角点。激光雷达无法读取印刷编码，
  它检测的是标定板对应的 **900×900 mm 竖直实体平面**。
- 任一路 USB/网络设备离线时，终端每 5 秒输出一次红色 warning，其余路继续工作。

当前车辆三颗 BPearl 的数据端口已按现场遮挡/靶板移动试验确认，不沿用旧车配置
中的顺序：

| 物理位置 | MSOP / DIFOP | ROS2 点云话题 |
|---|---:|---|
| 左前补盲 | 6702 / 7791 | `/sensing/lidar/front_left/pointcloud_raw` |
| 右前补盲 | 6700 / 7789 | `/sensing/lidar/front_right/pointcloud_raw` |
| 后侧补盲 | 6701 / 7790 | `/sensing/lidar/rear/pointcloud_raw` |

## 2. 启动与停止

在工控机桌面终端运行：

```bash
cd ~/white_ws/calibration/joint_extrinsic_station
./start.sh
```

浏览器访问 `http://127.0.0.1:8765`。页面显示 15 路状态、帧率、延迟、
Tag ID、雷达平面靶方向和预览。停止时运行：

```bash
./stop.sh
```

若本轮只补采交通信号灯相机与四颗激光雷达的外参数据，运行：

```bash
cd ~/white_ws/calibration/joint_extrinsic_station
./traffic_cam_start.sh
```

该专项网页仍使用 `http://127.0.0.1:8765`，但只显示交通灯相机的实时图像、
Tag16h5 检测结果、ROS 消息时间、工控机接收时间、当前新鲜度，以及四颗雷达的
在线状态。它不会打开六颗 USB 相机或四颗鱼眼相机，保存目录中也只会产生
`traffic_light_front` 一张 PNG 和在线雷达的 PCD；原有历史数据不会被删除。
退出时仍使用同一个 `./stop.sh`。若普通联合采集站已经运行，先停止后才能切换模式。

`stop.sh` 只停止采集站以及由采集站自行启动的雷达进程；如果启动前已经有四路
雷达发布者，采集站会复用且不会停止它们。PID 和 Linux 进程启动时刻会同时核验，
避免 PID 复用时误停无关程序。

## 3. 保存按钮与状态提示

保存按钮始终可点击。以下条件只作为页面上的摆放质量提示，不再阻止采集：

1. 4 路雷达和 11 路相机全部在线；
2. 车顶雷达在前、后、左、右四个区域各找到一块 900 mm 平面板；
3. 左前 BPearl 同时找到前板和左板，右前 BPearl 同时找到前板和右板，
   车尾 BPearl 找到后板；
4. `video_front_mid` 和 `video_rear_mid` 各看到至少一个 tag16h5；
5. 左前/左后相机至少一颗看到 tag，右前/右后相机至少一颗看到 tag。

四颗鱼眼和交通灯相机只显示检测结果。但要解算它们的外参，仍需在后续多组数据中
让它们各自至少 5 次清晰看到同一批标定板。雷达状态采用候选中心位置一致性判定：
当前候选需在最近 3 次检测中至少 2 次落在 0.45 m 范围内；摆好板后
需静止约 8–12 秒，避免单帧噪点或临时遮挡让状态提示误判。预览检测只抽样降频，
保存的仍然是在线雷达的完整原始点云和在线相机的原分辨率画面。

雷达平面检测会分别约束接近 900 mm 的横向宽度和可见高度；允许 32 线雷达只
扫到少量竖向线束，也允许板面向后倾斜。前、左、右板使用近地高度范围，后板使用
独立的悬挂高度范围。左右 BPearl 会在车顶雷达已经确认的物理板边界内检查自身回波，
而不是独立把柱子、墙面或挡轮块当作标定板。检测仅去除地面以上 15 mm 的窄噪声
带，完整原始 PCD 不做裁剪。

2026-09-02 使用移动标定板前后的两组静态 PCD 校正了左右 BPearl 粗略种子：
实测离地高度分别约 0.4503 m 和 0.4514 m；相对车顶雷达的 `z` 更新为
`-1.2744 m`、`-1.2789 m`。旧的 `roll=±90°` 会将真实地面映射为近竖直面，
已按地面法向改为 `pitch=-90°`，并利用前墙及柱子与主雷达点云重合度选择左
`yaw=-135°`、右 `yaw=135°`。这些仍是待标定板优化的可靠粗值，不是最终外参。

同一方法测得后 BPearl 离地约 `0.3792 m`，比左右两颗约低 `0.071 m`；其相对
车顶雷达的 `z` 更新为 `-1.3334 m`。有符号地面法向表明旧 `pitch=90°` 方向
翻转，已改为 `pitch=-90°`；四航向结构重合比较中 `yaw=0°` 的 20 cm 内重合率
约 62%，其余候选最高约 9%，因此以 `[0°, -90°, 0°]` 作为朝后粗略姿态。

离线或保存失败的传感器会输出红色 warning 并被跳过，其余数据继续写入。
`manifest.json` 会记录 `complete_sensor_set`、`missing_sensors`、
`failed_sensors`、建议条件是否满足及其原因。这样可以保存调试数据，但用于正式
外参求解时仍建议选择传感器完整、靶板清晰的组。

点击后会在 `~/white_ws/calibration/extrinsic_data/<时间>/` 原子保存：

- `lidars/`：4 个保留所有原始 PointCloud2 数值字段的 binary PCD；
- `cameras/`：11 张无损 PNG；
- `intrinsics/`：本次使用的全部已验收内参副本；
- `manifest.json`：ROS 时间、主机接收时间、软件同步偏差、检测结果和文件索引；
- 本次 `config.yaml` 与 `initial_extrinsics.yaml` 副本。

车辆、标定板或人员正在运动时不要点击。这里是“触发时各路最新帧”的软件同步，
不是硬件触发同步；静态靶板是保证对应关系成立的前提。

## 4. 首次现场配置

打印源文件和实时图像已经交叉确认：每块板是 **6 列 × 5 行、ID 0–29、按行递增、
ID 0 在左下角** 的 tag16h5 自定义 AprilGrid，而不是一块板只有一个大 Tag。
画面中看起来像5列×6行，是因为板旋转了90°。精确配置为：

```yaml
tag_board:
  outer_width_m: 0.900
  outer_height_m: 0.900
  active_width_m: 0.800
  active_height_m: 0.800
  columns: 6
  rows: 5
  id_order: row_major
  id_origin: bottom_left
  tag_size_m: 0.108
  horizontal_gap_m: 0.0304
  vertical_gap_m: 0.065
```

单个黑色 Tag 外框为108 mm；横向净间距30.4 mm，纵向净间距65 mm。因此横向
`6×108+5×30.4=800 mm`，纵向`5×108+4×65=800 mm`，四边各留白50 mm。
横纵间距不同，不能使用只有一个 `tagSpacing` 参数的标准 Kalibr AprilGrid。
整个6×5网格位于900 mm板中心，且安装平面不能鼓包。
四块板图案相同，因此求解器用粗略安装位姿将相机中的网格中心与车顶雷达检测到
的前/后/左/右物理板中心自动做最近邻匹配，不依赖四块板拥有不同 ID。

## 5. 推荐采集方案

### 初始摆放

车辆停在平整、空旷、光线均匀的位置并保持驻车。四块板均竖直、Tag 朝向车辆：

- 前板：车头前方约 3–5 m，略偏向能与左/右前补盲雷达共视的位置；
- 后板：车尾后方可放至约 3–10 m；为越过车尾盲区，可将整板比其余板抬高约
  1 m，保证车顶雷达、车尾 BPearl 和后中相机共视；
- 左板：车辆左侧约 2–4 m；
- 右板：车辆右侧约 2–4 m。

前、左、右板可直接立在地面，并允许向后倾斜约 8°–25°；后板按上面的悬挂
方案布置。车顶雷达必须无遮挡看到四块板。左/右前 BPearl 的有效区域是各自
前侧约 45° 半球：左前雷达必须同时看到前板与左板，右前雷达必须同时看到前板
与右板。若缺少前板，应先调整前板横向位置或绕竖直轴转动板面；若缺少侧板，
可将对应侧板适当向后移动，并把板面朝该 BPearl 转动约 15°–30°。不是先排除
左补盲雷达；四颗雷达从第一组开始全部参与。

### 多姿态数据

至少保存 10 组，推荐 12–16 组。每次只移动标定板，车辆和传感器不动；摆好后
静止 2 秒，确认状态稳定，再点击一次：

1. 基准组 2 次：四板约 3–5 m、基本竖直；重复一次用于检查重复性。
2. 距离组 3–4 次：分别改变到约 2 m、3.5 m、5 m；不要四板始终共面。
3. 横向组 3–4 次：在各自区域左右移动 0.5–1.0 m，让图案落在图像中心、边缘、
   上下位置；保证每颗待标相机至少 5 次看到 Tag。
4. 姿态组 3–4 次：绕竖直轴或水平轴轻微倾斜约 8°–18°，保持整板可见。
5. 鱼眼/交通灯补充组：尽量保留四板建议布局，只微调对应区域标定板，使四鱼眼和
   交通灯相机分别获得至少 5 个、最好 8 个清晰共视观测。

不要用连续 5 分钟视频代替这一流程：外参需要“同一静止时刻”的点云与图像配对。
相邻两组应在距离、横向或倾角上有明显变化，否则数学上会退化。

每组保存后检查 `manifest.json` 的 `software_receive_spread_ms`。交通灯相机只有
5 Hz，通常小于 350 ms 可以接受；超过 500 ms 建议保持静止并重采。

## 6. 数据校验与求解

先只检查数据完整性：

```bash
source /opt/ros/jazzy/setup.bash
source ~/white_ws/install/setup.bash
python3 solve_joint_extrinsics.py --validate-only
```

完成多组采集后执行：

```bash
python3 solve_joint_extrinsics.py
```

求解器以车顶雷达为参考，使用同一靶板的中心与法向量联合优化其余三颗雷达和
11 颗相机。鱼眼先按 `equidistant` 模型去畸变；普通镜头按 `plumb_bob` 处理。
输出为 `refined_extrinsics.yaml`，**不会自动覆盖 Autoware 的实时 TF**。
保存的 PCD 不裁剪墙面和柱体；这些稳定结构应在靶板初解后用于 RViz 叠加复核，
尤其检查墙角、柱边和地面交线是否在四路点云中重合。

仅根据用户描述的安装位置生成粗略矩阵、RPY和四元数：

```bash
python3 compute_initial_transforms.py
```

输出为 `calculated_initial_transforms.yaml`。它是联合优化的初始值，不是标定结果。

结果建议按以下标准验收：

- 中心 RMS ≤ 0.02 m、法向 RMS ≤ 0.5°：优秀；
- 中心 RMS ≤ 0.04 m、法向 RMS ≤ 1.5°：可接受，仍需投影复核；
- 中心最大误差 > 0.07 m 或法向 RMS > 1.5°：不应用，检查错 ID、板面弯曲、
  遮挡、点云靶板误检或采集姿态退化后重采。

最终还必须在 RViz/图像投影工具中复核：不同雷达在墙角、路缘和车辆轮廓处重合；
点云投影到原图后落在标定板边缘附近。确认通过后，才人工备份并更新
`white_sensor_kit_description/config/sensor_kit_calibration.yaml`。

## 7. 已知初值说明

`initial_extrinsics.yaml` 保存了原 5-in-1 配置中的三颗 BPearl 相对车顶雷达位姿，
以及按实车描述生成的 11 颗相机粗略初值。向下俯视在本文件坐标约定中使用正
pitch。左右前后普通相机的前后安装间距尚无实测值，因此相同侧两颗相机的平移
初值可能重合；它们只作为优化起点，不是最终标定值。
